# Previous vs current merge/split handling in `identifymcs_radar`

Scripts that compare how `pyflextrkr/identifymcs_radar.py` treats short merge/split tracks ("fragments")
before and after the commit *"identifymcs_radar: keep merge/split fragments that do not coexist with their root"*,
and that draw the figures used to explain the change.

**The change in one paragraph.** A short non-MCS track that merges into / splits from another track is folded into
that track's root, and its pixels are painted into the root's mask. The previous code painted only the time points at
which the root exists and then dropped the fragment track, so the fragment's other time points ended up in *no track*.
The current code folds a fragment only if **all** of its time points exist on the root's time axis; otherwise the
fragment stays a normal track and its pixels keep a track number. The check is repeated until nothing changes, because
releasing one track re-roots any chain that passed through it.

## Files

| File | What it does |
|---|---|
| `setup_comparison.py` | Prepares a work directory: exports the two code revisions with `git archive` (`code_old`, `code_new`), builds one root per version (`old/`, `new/`) from an existing tracking (stats copied, cloudid/track files hard-linked) and writes the two configs. Runs nothing. |
| `run_tree.py` | Runs `run_mcs_radar3d.py` from an exported code tree (identify + mapfeature) so both revisions can run on the same input. |
| `analyze_mask_difference.py` | One MCS, every time frame: 3-panel figure (previous / current / difference), time series, key-frame montage, mp4, `summary.json` (also totals over all MCS and what the Tb-style attach logic of `identifymcs.py` / `link_mergesplit_tracks.py` would do on this data). |
| `make_realdata_keyframes.py` | Real-data figure: left = root MCS, folded fragments and not-folded fragments, right = final MCS mask and the standalone fragments. |
| `make_synthetic_figure.py`, `synthetic_run.py` | Synthetic illustration: 8 made-up tracks run through the real code of each revision (and through `identifymcs.py` / `link_mergesplit_tracks.py`). Produces the full previous-vs-current figure, a version with only the current code, and a comparison with the other two modules. |

## Workflow

```bash
# 0. an existing tracking whose stats go through run_trackstats and whose config is an MCS (radar_feature) config
SRC=/path/to/tracking_root              # holds stats/ and tracking/
CFG=/path/to/config_mcs_radar.yaml
WORK=/path/to/scratch/mergesplit_compare
OUT=/path/to/figures

# 1. set up (login node is fine; hard links make it cheap)
python setup_comparison.py --workdir $WORK --source-root $SRC --config $CFG

# 2. run both versions (compute node; each takes a few minutes with 48 Dask workers)
python run_tree.py $WORK/code_old $WORK/old/config.yml
python run_tree.py $WORK/code_new $WORK/new/config.yml

# 3. figures
python analyze_mask_difference.py --workdir $WORK --outdir $OUT --tn 4525 --ref-time 2025-05-02T19:00:43
python make_synthetic_figure.py   --workdir $WORK --outdir $OUT/synthetic
python make_realdata_keyframes.py --workdir $WORK --outdir $OUT \
       --frame 4525 2025-05-02T19:00:43 --frame 4525 2025-05-02T15:20:39 --frame 12202 auto
```

`--tn` / `--frame` use the MCS track number of the **current** code (pixel `tracknumber` = index + 1 in the stats);
the previous number is found by matching the track's times and cloud numbers. `--frame ... auto` picks the time at
which the previous code attached the most fragment area that the current code does not fold. The default frames of
`make_realdata_keyframes.py` are the ones used for the original 2-day MRMS case; give `--frame` for other data.

## What to look at

* **Pixel variable**: the MCS mask including attached fragments is `cloudtracknumber`; `tracknumber` holds only a
  track's own features. Plot the former to see the whole MCS.
* **Output of `analyze_mask_difference.py`**: `only_prev_*` pixels left the MCS mask (they are now a standalone track),
  `recovered_*` pixels had no track before and have one now.
* The synthetic figures are generated by running the real code; nothing in them is drawn by hand except the layout.

## Notes

* Needs the environment used for PyFLEXTRKR plus `cartopy`, `matplotlib`, `PyYAML` and (for the mp4) `ffmpeg`.
* `setup_comparison.py` finds the old revision with `git log --grep`, so it keeps working after a rebase; pass
  `--old-rev` to use another revision.
* The two roots together need roughly the size of the pixel files of two runs (about 13 GB each for the 2-day
  MRMS case); the tracking files are hard-linked and cost nothing.
* `--new-rev` defaults to `HEAD`. Since `run_mcs_radar3d.py` got the second-pass step `run_regionprops` (it reads the
  `identifymcs_radar` file `mcs_tracks_`, writes the `mcsrobust_filebase` file that mapfeature reads, and needs
  `conv_feature_number` in the cloudid files), a run of `HEAD` on cloudid files made before that step cannot go through
  mapfeature. To reproduce this comparison on such a tracking, pass `--new-rev` the revision of the merge/split change
  itself (the commit titled *"identifymcs_radar: keep merge/split fragments that do not coexist with their root"*);
  `setup_comparison.py` writes both `finalstats_filebase` and `mcsrobust_filebase`, so that revision runs with the same
  config.
